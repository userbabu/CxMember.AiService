# 模型时段计费

每个模型支持三组独立输入、输出价，公开单位均为 credit / 1,000 模型 token，数据库以整数 microcredit 保存；1 credit = 1,000,000 microcredit。内部系数固定 10000，不作为运营配置。人民币售价仅用于后台计算器换算。

1. 常规价使用 `ai_model` 的现有价格。
2. 高峰价使用 `ai_model_pricing` 的每日起止时间，后台以单个区间输入，例如 `9:00-12:00`；保存时规范化为 `09:00` / `12:00`，继续使用既有字段。按该模型的 IANA 时区解释，默认 `Asia/Shanghai`。支持 `23:00-7:00` 跨午夜，起止相同、越界时间或多个区间直接拒绝。区间外使用低峰价，即既有常规价。
3. 限时活动价使用明确起止日期，由 PHP 按模型时区转换为 Unix 秒存储。

优先级：限时活动价 > 高峰价 > 常规价。每个计费时段分别配置输入、缓存命中输入、输出三种单价；缓存命中输入价默认 0。所有区间均开始包含、结束不包含。活动到期后直接恢复当时适用的高峰价或常规价，不需要定时任务。关闭活动或高峰计费会保留已填写的配置。

Go 完成模型查询时、进入限流队列之前锁定价格。预扣和最终结算都使用这个快照；排队、跨时段、跨活动终点或后台修改配置不会改变该请求的价格。当前按请求锁定一个价格时段，不会按请求持续时间分段计费；缓存命中输入另有独立价格。

上游 `usage.prompt_cache_hit_tokens` 或 `usage.prompt_tokens_details.cached_tokens` 报告的缓存命中数用于将输入拆分为普通输入与缓存输入。结算按 `(prompt_tokens-cached_prompt_tokens) × 输入价 + cached_prompt_tokens × 缓存输入价 + completion_tokens × 输出价` 计费，并应用同一倍率。缺少缓存明细的上游按零缓存处理；命中数大于输入总数或两个上游字段互相矛盾时拒绝该响应。

结算事务同时更新钱包、用量、账本和 `ai_usage_pricing`；任何一步失败都回滚。快照包含实际价格类型、输入/缓存输入/输出单价、倍率、计费时区及 UTC 锁价时间。删除模型或用量记录不会删除价格快照。预扣时缓存命中尚未知晓，因此按输入价与缓存价的较高值为所有估算输入预留，最终结算按上游实际命中数计算并释放差额。

## 部署与数据库

先执行 `migrations/003_model_pricing.sql`，再升级 PHP、Go 和后台前端。迁移新增两张表并给现有模型建立关闭时段计费的配置，不修改现有单价和余额。`ai_model_pricing.model_id` 引用现有模型主键，删除模型时级联清理其时段配置。缓存独立计价及供应商成本/利润率配置另需执行 `migrations/009_cache_pricing.sql`。新增的缓存用户单价与历史缓存 Token 数初始化为 0；供应商成本初始化为 NULL，利润率默认 20%，1000 credit 售价基准默认 5 元。迁移不改变既有用户扣费单价或余额。

执行前检查 `cx_ec`、`ai_model` 主键及字符集，确认两张新表名不存在。MySQL DDL 会隐式提交；创建失败必须停止，核对已完成步骤后处理，不得把部分创建视为成功。业务记录初始化为单条 INSERT。只有尚未启用新代码、且没有新的价格快照时，才可以通过删除这两张新表撤回结构；已经发生计费后不得删除快照作为回滚手段。升级前后都应核对模型数与配置数一致。

如表结构迁移后暂停发布、旧后台仍继续创建模型，切换新服务之前必须检查缺失配置并显式初始化，不能直接重跑 CREATE TABLE。初始化只插入缺失模型，不覆盖已设置的价格：

```sql
INSERT INTO ai_model_pricing(model_id)
SELECT m.model_id FROM ai_model m LEFT JOIN ai_model_pricing p ON p.model_id=m.model_id
WHERE p.model_id IS NULL;
```

可通过项目根目录 `Dockerfile` 构建新 Go 镜像；运行时环境使用本地 `.env`，不写入镜像。镜像包含 HTTPS 根证书，Go 的 IANA 时区数据嵌入在可执行文件中。

模型导入和保存都在业务事务内创建配置。后台保存会验证 IANA 时区、单个高峰区间、真实活动日期、起止先后及三组 credit 价格；内部系数固定为 10000，无效配置直接失败。低峰、高峰及活动各自保存未命中输入、缓存命中输入、输出供应商成本（元/百万模型 Token），共用模型的目标利润率和 1000 credit 售价基准。自动计算分别使用各时段自己的成本，只回填该时段用户单价；未填写已启用时段的输入或输出成本时直接提示补齐，不以低峰成本替代高峰或活动成本。缓存成本未配置时保留该时段手工缓存单价，已配置为 0 时明确计算免费缓存价。成本与用户扣费字段独立，计算后仍允许逐项手工覆盖。利润率公式为 `成本 × (1 + 利润率) ÷ 每 1000 credit 售价`，按每千模型 Token 换算并向上取整到 microcredit。

分时段供应商成本要求 `migrations/013_period_supplier_costs.sql`：向 `ai_model_pricing` 新增高峰/活动共六个可空 unsigned BIGINT 成本列。历史 NULL 表示尚未配置成本，不回填或改变客户扣费单价。MySQL 5.7 DDL 隐式提交；先备份、确认六列不存在，再由用户执行一次，发布前只读核验类型、可空性和默认值。回退先恢复旧后台并导出已填成本，再删除新列，不能直接丢弃成本配置。高峰区间输入本身不需要修改表结构，实际计费仍由 Go 在入队前锁定三类价格。

## 验证

`go test ./internal/relay` 覆盖区间边界、跨午夜、UTC 与北京时间转换、活动优先级、到期恢复、锁价和无效配置。`TestPricingSettlementTransaction` 只在显式提供隔离库 `AI_PRICING_TEST_DSN` 时运行，验证钱包和价格快照的原子提交以及快照冲突时的回滚。不得给该测试传入业务库连接。


后台仅设置 credit / 千模型 token 的最终输入、输出价格，不提供倍率输入；内部系数固定为 10000。既有金额通过 004 等值换算，新 API 返回精确 credit 单价字符串。

## Credit 单位

所有时段的价格、预扣和锁价快照使用同一 credit 体系。原有价格与历史快照通过 004 迁移乘以 1000 转为真实 microcredit；对外单价等于原值除以 1000，经济价值不变。计算器以 1000 credit 售价和每百万模型 token 成本/毛利计算，结果精确到六位小数。完整公式、API 及切换流程见 [Credit 计费单位](credit.md)。

## 多模态 token 独立价格表

含图片的整个请求采用独立的多模态token表；不试图从总prompt_tokens虚构图片token，也不额外按张收费。输入包括图片与文字合计，缓存命中部分按该表缓存价、其余输入按该表未命中价、输出按该表输出价。纯文字请求继续使用普通token表。判断范围是完整messages上下文，因此历史仍包含图片的追问和工具续轮仍使用多模态表。

低峰、高峰及活动各有输入、缓存输入、输出三项最终credit/千token价格和三项供应商成本（元/百万token）。共享已有时区、高峰单区间与活动时间，优先级仍为活动>高峰>低峰；供应商成本只用于计算器，不直接扣款。两类计算器分别使用各自的时段成本，共用利润率/1000credit售价基准，不相互覆盖。可空缓存成本保留手填价格，明确0成本才自动计算0价；缺少已启用时段输入/输出成本时中断计算。金额仍使用microcredit整数和六位精确文本。

Go在图片验证之后、排队和预扣之前锁定价格表与时段；后续改价或跨时段不改变本次价格。结算使用供应商真实prompt/cached/completion usage，按照已锁定表计算一次；未返回usage时沿现有估算规则，不把base64算作普通文本。ai_usage_pricing.billing_input_kind记录text/vision，原有快照单价字段记录实际采用的价格。历史快照的text标记表示原价格表，不推断历史请求是否带图片。

017_vision_token_pricing.sql新增ai_model_pricing的9个售价和9个成本列，并从当前各时段普通价格/成本显式初始化；不改变普通价格、钱包、账本或历史单价。新增快照标记默认text以对应历史实际采用的原价格表。DDL隐式提交，先备份三表、确认所有新字段缺失和pricing行完整，由用户执行一次再只读核验后发布。回退先导出多模态配置和快照标记并恢复旧代码；不能丢弃财务历史或自动重算账单。


## DeepSeek 官方视觉

官方图像指南（https://api-docs.deepseek.com/zh-cn/guides/vision/）明确deepseek-flash及旧视觉别名支持图片，图片按尺寸折算token并与文本合计；单图token上限1024，并非按张另加固定费用。Go仅对HTTPS官方api.deepseek.com的上述两个上游模型采用1024图片预算，支持detail=original；第三方代理、其他模型及非官方端点保持8192预算，不按名称猜测官方能力。此预算用于上下文/TPM/预扣及原有缺usage估算，正常实际结算仍使用供应商usage与锁定多模态价格表，低峰/高峰/活动及缓存价不变，不重算历史账单。

现有EC本地上下文估算仍保守使用8192/图，不作为扣费依据。应用的PNG/JPEG、4MiB单图、2048像素边长等限制仍保留，不宣称实现供应商的所有格式、Files API或更大上传配额；EC现有内嵌data URL可直接使用。后台需对真实支持的上游模型手动开启allow_images并设置多模态价格，不自动更改模型或财务配置。


图片/视频生成的接口、独立模型能力、按张/按秒分时计费、持久任务恢复及客户端设置见 [图片与视频生成](media-generation.md)。
